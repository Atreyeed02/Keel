# Changelog

Notable changes to Keel, newest first. Versions follow
[Semantic Versioning](https://semver.org/). Before 1.0.0 there were no
releases: the project was built in pull requests #1 to #43, recorded in
[docs/STATUS.md](docs/STATUS.md).

## [1.0.0] - 2026-10-23

The first release. Keel is a double-entry ledger: a small accounting
service that records money moving between accounts, where every
transaction must balance and every balance can be rebuilt from an
append-only history of events. It has a JSON API and server-rendered pages
that teach the accounting as you use them, and it runs as a public demo at
[keel-htwz.onrender.com](https://keel-htwz.onrender.com). The
[README](README.md) is the place to start; [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)
explains every design decision.

### Ledger and data integrity

- **Double-entry, per currency.** Every transaction is a set of debit and
  credit entries whose totals must be equal in each currency it uses.
  Every debit is matched by equal credits, so the books always balance.
- **Rules enforced twice.** Each rule is checked in Python, for readable
  errors, and again by PostgreSQL triggers, so it holds even for writes
  that bypass the app: the balance (checked when the transaction commits),
  each entry's currency matching its account's, and an account's currency
  never changing.
- **Exact money.** Amounts are `NUMERIC(18,2)` in the database and
  `Decimal` in Python, never floating point, and always positive: the
  direction is the entry's debit or credit side.
- **Five account types** (asset, liability, equity, revenue, expense), each
  with its normal side, and balances signed by it.
- **All or nothing.** A transaction's entries and its event are written in
  one database transaction.
- **Idempotent postings.** Every posting carries a key, and one key gives
  exactly one ledger effect, even when retries arrive at the same time: the
  key is claimed first, with `INSERT … ON CONFLICT DO NOTHING`. A retry gets
  the original transaction back; the same key with a different request is a
  `409`. Keys older than 30 days can be pruned by a script.
- **Capacity caps** on accounts and transactions (200 and 2,000 by
  default, `0` for none), so the public demo can't fill its database.

### Event log

- **The event log is the source of truth.** Every change is first appended
  as an event (`account.created`, `transaction.posted`) with its full
  payload, and a trigger refuses any `UPDATE`, `DELETE` or `TRUNCATE` on it.
- **Balances are a projection.** The account, transaction and entry tables
  are written in the same database transaction as the event, and can be
  thrown away and rebuilt from the log with
  `python -m scripts.rebuild_read_model`. The rebuild reports every balance
  it corrected, and postings wait for it rather than get lost.
- **Recorded order is kept.** Events are totally ordered, payloads carry a
  schema version, and each entry keeps its position in the transaction as
  submitted, so a rebuild reproduces the ledger exactly.
- **Backfill for older ledgers.** Accounts created before `account.created`
  existed get their events appended by a script before a rebuild will run.

### API and forms

- **A JSON API** under `/api/`: create and list accounts (with debits,
  credits and a signed balance), post a transaction with an
  `Idempotency-Key` header, and read one back. Amounts are strings, never
  JSON numbers, and every error has one shape:
  `{"error": {"code": …, "message": …}}`.
- **HTML forms** for creating accounts and posting transactions, using the
  same domain rules and the same idempotency as the API. Every refusal is
  worded by the rule it breaks and marked on its line, with what was typed
  kept. The forms work without JavaScript.
- **Interactive API docs** at `/docs`, generated by FastAPI.
- **`/health`** reports whether the database is reachable, and always
  answers.
- **`HEAD`** works on every page and API read.

### Educational UI

- **Eight server-rendered pages**: the overview, the posting form, a new
  account, the transaction list (search, date filters, pages), a
  transaction's page, an account's page, the event log and Learn.
- **The overview** shows the accounting equation for each currency,
  recomputed from the ledger: Assets = Liabilities + Equity + (Revenue −
  Expenses). On the demo, three "try it" steps open the posting form filled
  in.
- **The posting form** shows a live balance panel per currency as you type,
  and posts nothing until the transaction balances.
- **Account pages are T-accounts**: debits on the left, credits on the
  right, each entry with the accounts on the other side of its transaction,
  and the sum that gives the balance.
- **The event log** reads as a timeline, each event in words from its own
  payload, with the raw event one click away.
- **Learn** explains double-entry with worked examples and a short quiz, and
  every accounting term on the other pages is defined where it appears.
- **Built for everyone**: light and dark themes, phone and desktop layouts,
  keyboard use, a skip link, screen-reader announcements on the posting
  form, and animations that stop for reduced motion. Fonts and icons are
  served by Keel itself.

### Security and hardening

- **A strict Content Security Policy**: every script, style, font and
  image comes from Keel itself, and no page has an inline script or style.
  Plus `nosniff`, `X-Frame-Options: DENY` and a same-origin referrer
  policy, on every response.
- **A request body limit** (64 KiB by default): a larger body is refused
  with a `413` before it is read, with or without a declared length.
- **A per-client write rate limit** (30 writes a minute by default) shared
  by the forms and the API, with an exact `Retry-After`.
- **The right client behind proxies.** Forwarded headers are believed only
  from configured proxies, and Cloudflare's `CF-Connecting-IP` only when the
  request really came through Cloudflare, so no client can forge its way to
  a fresh rate-limit allowance. A weekly workflow checks the copy of
  Cloudflare's address ranges.
- **Refuses unsafe settings at start.** In production or on the demo, Keel
  won't start on the local default database, without TLS to Postgres, or
  trusting every proxy, and it warns when two TLS settings disagree.
- **Secrets stay out of logs.** The database password never appears in a
  log line or error, and what visitors type into the forms is never logged.

### Deployment and operations

- **One Docker image** that migrates the database and then serves, as an
  unprivileged user. It holds only the runtime packages, and base images
  are pinned by digest, from the repository's own mirror on ghcr.io.
- **Live on Render with Neon Postgres**, deployed from `main` on every
  merge. Keel runs as a single instance.
- **Nightly demo reset** on GitHub Actions, which restores the demo data in
  one transaction, after checking that it is connected to the live
  database.
- **Structured JSON logs** with a request id on every request and ledger
  identifiers on every write.
- **Maintained dependencies.** Dependabot proposes updates weekly, in
  groups, and every update is reviewed against Keel's code before merging.

### Testing and CI

- **483 automated tests**, 161 of them against a real PostgreSQL: the
  invariants and triggers, idempotency under concurrent retries, rebuilds,
  every API status code, every page, the security headers, the rate limit,
  the proxy rules and the deployment configuration.
- **Two required CI checks** on every pull request: lint, a dependency
  audit, a check that the migrations match the models, and the full test
  suite; and a smoke test that builds the image, starts it and posts a
  transaction over HTTP. `main` accepts changes only by pull request.
- **Before-and-after screenshots, as a review step:** before each pull
  request, every page is captured in both themes on desktop and phone, on
  `main` and on the branch, and compared pixel by pixel.
